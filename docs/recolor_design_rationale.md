# 再着色「色・明度を壊さない補正」の設計根拠とロードマップ

対象: `Code/Core/PixelProcessor.cs` / `Code/ColorZone.cs` ほか再着色パイプライン全般
関連: [`image_processing_math_review_2026-06-10.md`](image_processing_math_review_2026-06-10.md)（中核の数学的正しさを検証した記録。本書はその上に設計思想を重ねる）

この文書は「テクスチャの色・明度を壊さないための補正処理は、違和感を生じさせない方法として原理的に正しいのか、もっと良い発想があるのか」という問いに答えるための設計判断の記録である。コードの実装位置（`file:line`）を併記し、後続の改善判断の拠り所とする。

---

## 1. 結論（先に答える）

- **中核（OkLab + L の 2 区間リマップ + 彩度の target 色相均一化）は正当**。知覚均等空間で単調・端点保存・リング除去を満たす標準的な設計であり、数学レビューで全桁検証済み。**ここは疑わなくてよい**。
- 違和感の多くは中核の欠陥ではなく、**「単一アンカーの色転写」という近似モデルと、理想である「反射率×陰影の分離」とのギャップ**を、多数の補正パスが各所で個別に埋めている“税金”に起因する。これが「設計がとっ散らかって見える」正体。
- **より良い発想は存在する**（ガマットマッピングでハックを退役 → 乗算シェーディングで複数パスを統合）。ただし本ドメイン（手描き低解像度アバターテクスチャ・物理照明 GT 無し・1 クリック指定）では、真の反射率分離への全面作り直しは過剰でブリトル。
- **現実解は「中核を維持しつつ、原理的改善でハックを段階的に退役する」**。残る違和感の一部（地色が本質的に曖昧＝暗赤 vs 灰など）は色では分離不能で、**再着色数式でなくマスク（領域分離）案件**である。

## 2. なぜ中核が「正当」か

### 2.1 OkLab を使う理由
再着色の本質は「色相・彩度を変えつつ、明度・陰影（立体感）を保つ」こと。RGB や HSV の明度軸は知覚的に非線形で、色相を変えると人間の目には明るさが変わって見える。OkLab は知覚均等性を持つため、**色相を変えても明度・陰影が知覚的に保たれる**。これが「違和感を出さない」ための土台になる。

### 2.2 L の 2 区間線形リマップ（不動点 sL→tL）
`PixelProcessor.cs:2283-2286`。`[0,sL]→[0,tL]`, `[sL,1]→[tL,1]` の折れ線写像。
- **単調**（リング＝色の反転が出ない）・**端点保存**（黒→黒 / 白→白）。
- 不動点 `sL→tL` で base 明度を target 明度へ寄せる。L を完全保持すると暗色→黄が brown 化するため、base を target 明度に合わせるのが正しい（`:2253-2255` のコメント）。
- 彩度ゲート付きリマップ（`:2287-2299`）: 低彩度画素では remap を抑えて元 L を保持。相対 chroma 比（`oC/(sC·FULL_FRAC)`）で判定するため**色非依存**。AA 縁の白/灰ノイズを構造的に防ぐ。

### 2.3 彩度（a,b）を target 色相方向へ均一化
`PixelProcessor.cs:2256-2282`。大きさは元 chroma に比例、向きは target 色相に統一。
旧版の「色相回転保持」は単色ロゴの AA 縁にオレンジの色相ノイズを生んだ。向きを揃えることで L を保ったまま色相を均一化し、**色相ノイズを構造的に除去**する。

### 2.4 数学レビューによる裏付け
`image_processing_math_review_2026-06-10.md` で次が検証済み: OkLab 変換行列・sRGB 伝達関数が Björn Ottosson リファレンスと全桁一致／α 分解は BG→sample 直線への正射影として正しい／分離型ガウシアンはエネルギー損失なし／多ゾーン合成は凸結合（partition of unity）。**中核の数学的正しさは確立している**。

## 3. 違和感はどこから来るか — 「近似の税金」という見立て

### 理想モデル
各画素 = **反射率（albedo＝地色。置換すべき成分）× 陰影（shading＝立体感/光。保存すべき成分）**。
もし両者をきれいに分離できれば、再着色は「反射率の色相だけ差し替え、陰影をそのまま掛け直す」だけで済み、**原理的に補正パスは不要**になる（＝intrinsic image decomposition）。

### 現行モデルは安価な近似
現行は **単一グローバルアンカー**（スポイトでクリックした色＝「地色」とみなす）＋ 画素ごとの明度偏差＝「陰影」、という近似。十分に実用的だが、次の箇所で近似が漏れる:

| 漏れる場所 | 物理的な理由 | 当てている補正 |
|---|---|---|
| AA 境界 | 1 画素が 2 色の混色（`α·FG+(1-α)·BG`） | Decontamination（α 分解再合成） |
| 鏡面ハイライト | 地色でなく「光」が支配 | HighlightWash（軸射影） |
| 深い影 | 暗部の彩度がノイズ化 | shadowDesaturation |
| 無彩ターゲット | 立体感が知覚的に平坦化 | FormGain / SolidifyAchromaInterior |
| ガマット外純色 | 高 L×大 chroma が sRGB の外で陰影が潰れる | outputSaturation / ChromaAmpMaxFactor |

各補正パスは「1 つの漏れ」を塞ぐ正当な対処だが、**“数の多さ”自体が「単一アンカーは近似である」というシグナル**である。

## 5. パスを足し／減らす判断基準

新しい違和感が出たとき、対処の前に問う:

1. **これは単一アンカー近似の「漏れ」か、真に新しい現象か**。漏れなら、ローカルパッチを足す前に**分解（アンカー推定・陰影モデル）の改善で消せないか**を先に検討する。
2. **マジックナンバー禁止**: パッチがテクスチャ統計（ヒストグラム・彩度分布・領域サイズ比）から導けない固定値を要求するなら、それは過学習の入口。「パスを足す」でなく「モデルを上げる」合図。
3. **パス同士が打ち消し合い始めたら**統合のサイン（例: 増幅パスと脱彩パスが互いを相殺）。
4. **汎化最優先**（`improvement-cycle.instructions.md`）: テストセットだけで効くパスは“税金が腐った”状態。複数キャラ・複数衣装で横断検証する。

### 「アルゴリズムだけでどこまで行けるか」への回答
中核＋原理的改善（ガマットマッピング、乗算シェーディング）で違和感の大半は到達できる。残る違和感は**地色が本質的に曖昧な領域**（暗赤 vs 灰、純白 vs 淡彩）で生じ、これは色情報だけでは分離不能で**マスク案件**。アルゴリズムでなく領域指定（マスク UI）で解くべき境界がある、というのが上限の見立て。

## 6. 改善ロードマップ

実装は **1 Tier = 1 改善サイクル = 1 コミット**。複数を混ぜない（どれが効いたか分かるように）。

### Tier 1（低リスク・原理的・ハック退役）— ガマットマッピング
OkLab→RGB 変換でガマット外に出た色を、現状のチャンネル別 `Clamp01`（`PixelProcessor.cs:2234-2236`＋`:2329`、L と色相が歪む）から、**L・色相を固定して chroma(a,b) だけを二分圧縮**する方式に置換。`a,b` を同率縮小するので色相角 atan2(b,a) は不変、L も不変。in-gamut 画素はバイト完全不変。`outputSaturation` を手で下げる必要を構造的に減らす。数学レビュー 2.1 が自己特定済みの最有力手。

### Tier 1.5（整合修正）
数学レビュー 2.3〜2.5。relaxed/本体のグレー判定統一（`chromaThreshold` を引数伝播）／シャドウ免除係数の整合／`chromaThreshold > 0.30` の Lerp 方向保証。内部不整合由来の違和感を消す。

### Tier 2（中リスク・統合）— 乗算シェーディング核
アンカー推定が既に使う `satr = C/L`（乗算シェーディング不変量、`PixelProcessor.cs:1242-1316` 付近）を中核 recolor に昇格し、`recolor = 新地色 × 局所シェーディング比`へ。FormGain / SolidifyAchromaInterior / valueBlend 一部を一原理に統合できる可能性。改善サイクルで検証し、効果が出なければ不採用。**ユーザー方針（valueBlend は原則下げない／edgeFeather は原則 0）と矛盾しない範囲に限定**。

### Tier 3（研究・保留）
真の反射率/陰影分離（intrinsic image / guided filter）。照明 GT 無しの手描き低解像度テクスチャには過剰の公算大。理論上限として記すに留め、実装は当面しない。

## 7. ユーザーの具体的懸念への回答

> idea2.md:「スポイトした色が暗いときに明るい色を出力に設定するとかなり明るくなってしまうのはおかしい」「均一な色になるようにしつつ、ユーザーが明るい色を望めばそうするようにすべき」

これは **autoRecolorAnchor**（代表地色 P90 を統計推定しスポイト位置非依存にする、`PixelProcessor.cs:1242-1316`）＋ brightness cap で**既に原理的に対処済み**（コミット 29fd711 ほか）。
重要なのは、この修正が「ローカルパッチを足す」のではなく「**アンカー推定＝分解を改善する**」という第 5 節の正しい打ち手だった点。ユーザーの直感は正しく、L リマップ＋アンカー正規化の組み合わせが「均一にしつつ、望めば明るく」を達成している。
