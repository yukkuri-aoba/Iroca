# 自律的な改善サイクル

色抽出・マスク生成・領域判定など再着色アルゴリズムの品質改善は、**ユーザーの都度指示を待たず、エージェント自身が自律的にサイクルを回して** 進める。1 ステップごとに「次やりますか?」と聞かない。

## 測る対象は常に「実 C#」
- **製品 C#（`Code/Core/PixelProcessor.cs` ほか）が唯一の正。** 改善の良し悪しは、実 C# をそのまま動かす headless ハーネス経由の出力で判定する。アルゴリズムの Python 再実装を作って測らない（過去、Python プロキシが製品から IoU 0.26 乖離して改善サイクルが製品でなくプロキシを測っていた）。テスト構成・実行方法は `docs/testing-architecture.md` が正。

## 正解データ (Ground Truth)
- **PSD のレイヤー情報を「正」とする。** GT マスク/領域は `dev_safe/scripts/` 配下の GT 生成スクリプト（`build_*_gt.py` / `analyze_*_psd.py` 等）で PSD から作る。
- テクスチャ単体の目視結果や経験則は補助情報。PSD レイヤーと矛盾したら PSD を優先する。
- GT が不足しているなら、GT なしで「改善した」と主張せず、新しい GT を追加する。

## サイクルの基本形
1. **現状計測** — 実 C# ハーネス経由のテストでスコア・失敗ケースを数値で把握する:
   ```
   python -m pytest dev_safe/Tests/regression/ -q
   ```
2. **失敗分析** — 最もスコアを落とす／誤検出・見逃しが目立つケースを特定し、原因を具体的に仮説化する（色空間、閾値、連結成分処理、マスク膨張/収縮など）。
3. **変更前スナップショット** — 変更前に必ず実行（旧出力を保存。すでに変更済みならスキップ可）:
   ```
   python tools/visual_review.py snapshot
   ```
4. **変更** — 仮説に基づく最小の変更を 1 つだけ加える。複数の改良を同時に混ぜない（どれが効いたか分からなくなる）。
5. **再計測** — 同じテストを実行し、全体スコアと個別ケースの変化を比較する。
6. **視覚的レビュー（必須）** — 数値だけで判断せず、出荷される実 C# 出力で目視する:
   ```
   python tools/visual_review.py compare --engine csharp
   ```
   生成された比較パネル PNG を **Read ツールで 1 枚ずつ** 確認する（各画像は「元テクスチャ／変更前／変更後」の 3 列構成）。全ケースで以下をチェックする:
   - 元テクスチャにない質感・ノイズが追加されていないか
   - 変換対象エリアに変換漏れがないか
   - 関係ない部分が変わっていないか（**全体サムネイルで必ず確認**）
   - テクスチャを切り出して作業した場合も、全体サムネイルで切り出し範囲外が変わっていないか

   問題があれば採用せず手順 4 へ戻る。問題がなければ承認マーカーを書く:
   ```
   python tools/visual_review.py approve
   ```
7. **判定** — IoU スコアと視覚レビューの両方が OK なら採用。悪化・横ばい、または視覚的問題があれば破棄か別仮説へ。**改善が頭打ちになるまで 4〜6 を繰り返す。**
8. **記録** — 何を試して何が効いた/効かなかったかを簡潔にまとめ、最終報告に含める。

## 停止条件
次のいずれかでサイクルを止めて報告する。
- 指標がこれ以上有意に改善しない（数回試して改善幅がノイズレベル）。
- さらなる改善に GT の追加・仕様判断など **ユーザーの判断が必要**。
- 変更範囲がユーザー要求の外に広がりそう（勝手にスコープを広げない）。

## 汎化能力を最優先する
このツールの価値は「手元の数枚で完璧に動く」ことではなく、**未知のテクスチャでも妥当に動く** こと。改善サイクルは常に汎化を意識して回す。

- **評価は複数キャラ/複数衣装を横断して行う。** `dev_safe/Tests/regression/` の `*_iou` 系・`false_positive` 系などを **できるだけ全て** 回し、個別スコアと平均の両方を見る。単一ケースの改善だけで採用しない。
- **1 ケース改善しても他ケースが悪化したら原則不採用。** 避けられないトレードオフは、悪化幅が小さく全体平均が向上することを数値で示し、理由を報告に残す。
- **特定キャラ名・ファイル名・ピクセル座標・色値で条件分岐しない。** 閾値・係数はテクスチャの統計量（ヒストグラム、彩度分布、領域サイズ比など）から導く。マジックナンバーを足すなら、なぜ他でも妥当かを説明できること。
- **過検出を見ないテスト（`false_positive` 系）を特に重視する。** 再現率(Recall)だけでなく適合率(Precision)を同時に見る。
- 迷ったら、**より単純で仮定の少ない方** を選ぶ。複雑なヒューリスティックは未知データで壊れやすい。

## やってはいけないこと
- GT と突き合わせずに「良くなった気がする」で終える。
- 手元のテストデータに最適化したパラメータを入れる（＝過学習）。個別ケースを通すためのハードコードや、テクスチャ名・ハッシュ・特定色・座標を直接参照するロジックも同じ。
- テストを削除・無効化して「パスした」と報告する（必要なら `[Ignore]` でなく理由をログに残す）。
- 悪化した変更をコミット対象に残す。
- 視覚的レビューを省略してコミットする（`compare --engine csharp` → Read で 1 枚ずつ確認 → `approve` の順を飛ばさない）。これは pre-commit フックが要求する出荷ゲートであり、「念のための再確認」ではない。省くと数値では見えない退行が出荷される。
