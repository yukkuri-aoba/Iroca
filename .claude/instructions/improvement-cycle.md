# 自律的な改善サイクル

色抽出・マスク生成・領域判定など再着色アルゴリズムの品質改善は、**ユーザーの都度指示を待たず、エージェント自身が自律的にサイクルを回して** 進める。1 ステップごとに「次やりますか?」と聞かない。
テストの作りと実行方法の正は `docs/testing-architecture.md`。経緯（2026-11-20〜21 のテストの作り直し）は dev_safe の `docs/test-validity-audit-2026-11-20/README.md`。

## 前提
- **製品 C#（`Code/Core/Pipeline/PixelProcessor.cs` ほか）が唯一の正。** 良し悪しは、実 C# を動かす headless ハーネスの出力で判定する。アルゴリズムを Python で再実装して測らない（Python の写しが製品から IoU 0.26 離れ、プロキシを測っていた事故がある）。
- **入口は窓で行き着く状態だけ**: (a) クリックした直後（自動調整なし。AI が使えないとき・「スポイトで色を選んだら自動調整する」がオフのとき）、(b) 自動調整の後（スポイトでクリックしたときの既定）、(c) その後の手直し、(d) 右クリックの後。Python 側の入口は `dev_safe/scripts/oneshot.py` の 1 つで、ハーネスの `--oneshot`・`--script` が製品の段取り（`AutoTuneFlow`・`SamProposalFlow`・`ZoneEdits`・`MaskWorkspace`）をそのまま回す。Python に段取りを書き写さない。クリックは面の内側から選ぶ。
- **正解（GT）は PSD のレイヤー情報。** dev_safe の GT 生成スクリプト（`scripts/build_*_gt.py`・`analyze_*_psd.py` 等）で作る。テクスチャの目視や経験則は補助で、PSD と矛盾したら PSD を優先する。GT が足りないなら、GT なしで「改善した」と言わず GT を足す。
- **ユーザーが絵で選んだ答え（お手本）は、PSD の GT と別の正解。** 見た目の判断（基準色の明るさなど）はお手本で決める。

## テストの役目と、落ちたときの意味
回帰テストの関数ごとの役目と入口は `dev_safe/Tests/regression/roles.json`（台帳）が正。台帳に無いテストは収集エラーになり、実行の終わりに役目ごとの結果と「落ちた意味」が出る。役目ごとの扱い:
- **契約**（仕様から言える不変条件）: 落ちたら不具合。直すまでコミットしない。値を付け替えない（仕様を変えるときだけ）。
- **お手本**（`dev_safe/Tests/exemplars/`）: 幅を動かさず製品を直す。結果が「ユーザーが見ていない明るさ」（`unseen`）へ動いたら、はしごの絵を作ってユーザーに聞く。手順は `dev_safe/Tests/exemplars/README.md`。
- **物差し**（正解に照らした数字。凍結した基準からの退行や、変更前後の比較で見る）: 退行の幅と絵で判断する。採用したら基準を進める（下の「基準を進める」）。
- **変化の検知**（前の出力との突き合わせ）: 視覚レビューに一本化してある。目で見て判断する。
- **基盤**（測定器そのもの）: 製品とは別に直す。
- **到達目標**（xfail、strict=False）: 落ちても通る。XPASS したら目標を進めるか、契約へ移す。

## サイクルの基本形
1. **現状計測** — 実 C# の出力でスコアと失敗ケースを数値で把握する。テストはテスト用 PC（G83）で回す（`python tools/remote_test.py -- …`。つながらなければ手元で回る。仕組み・スロット・持ち帰りは `docs/testing-architecture.md` の「テスト用の別 PC で回す」）:
   ```
   python tools/remote_test.py -- -m pytest dev_safe/Tests/regression/ -q
   ```
   - 採否判断に使う計測（この手順 1 と手順 5）では **`IROCA_GATE_FULL=1`** を立てる。立てないと品質ゲートは一部の被写体・ワンショットは p50 しか測らず、残りを測らないまま「全パス」と見誤る（2026-11-20 に 1 つにまとめた。系統ごとの名前は `dev_safe/Tests/regression/gate_scope.py`）。
   - 重い計測スクリプト（`generalization_report.py run`・`color_report.py run`・`highlight_recall.py run`・`probe_*`・`measure_*`・`sweep_*`）・abcheck・EditMode（`tools/editor_tests.py`）・試作の DLL（`--dll`・`IROCA_HARNESS_DLL`）も同じ入口で回し、結果のファイルは `--fetch <本体からの相対パス>` で持ち帰る。compare・sweep・freeze は軽いので手元で回す。
   - `holdout_eval.py` は見た回数を `dev_safe/Tests/Baselines/holdout_log.jsonl` に記録するので、回したら必ず `--fetch dev_safe/Tests/Baselines/holdout_log.jsonl` で持ち帰る。
   - 視覚レビューの snapshot・compare は相手が使えれば自動で相手で回る（approve・check は手元）。snapshot と compare は同じ所で回す。
2. **失敗分析** — 最もスコアを落とすケース・誤検出・見逃しを特定し、原因を具体的に仮説化する（色空間・閾値・連結成分・マスクの膨張/収縮など）。
3. **変更前スナップショット** — `python tools/visual_review.py snapshot`。既定で **HEAD のコード**をビルドして撮る（他人の未コミットも入らない）。変更前が HEAD ならコードを変えた後に撮ってもよい。HEAD 以外は `--rev <コミット>`、作業ツリーのままなら `--worktree`。測定器（`tools/`・dev_safe の測定スクリプト・基準）を変えるときは**変える前に**撮る（snapshot は測定器を作業ツリーのまま動かす）。approve は、変更前と同じ中身を測った比較（変化 0 が何も示さない）を断る。
4. **変更** — 仮説に基づく最小の変更を 1 つだけ加える。複数の改良を混ぜない（どれが効いたか分からなくなる）。
5. **再計測** — 同じテストを回し、全体と個別ケースの変化を比べる。選択か再着色を変えたなら、下の「採否の物差し」も回す。
   **ふるい**（2026-11-15〜。採否の判断を変えずに計算と電力を減らす。1 件で不合格が決まる条件だけで止めてよい）:
   - 汎化レポートは `run --label <名前> --sieve` で回す。ケースごとに基準（既定は freeze した基準。別の A と比べるなら `--sieve-base <A.json>`）の退行床と比べ、違反が 1 件出たら止まる（終了コード 3）。そのケースは全件を回しても同じ値で違反になるので結論は変わらない。止まらなければ `--sieve` なしと同じ JSON ができる。平均で決まる条件は途中では決めない。
   - 回帰の pytest は、案を試す 1 回目は `-x` を付けてよい（1 件でも落ちればコミットできないので結論は同じ）。
   - 止まった案を「避けられないトレードオフ」として採りたいときだけ、`--sieve`・`-x` なしで全件を回して数値で示す（測った分はキャッシュに残る）。
   - 視覚レビュー（手順 6）とホールドアウトは、数値が通った案だけで回す。
   - 色の物差し（`color_report.py run`。G83 で 1 回 20〜30 分）は、回帰（`-x`）と汎化レポート（`--sieve`）が通った案だけで回す（2026-11-24〜）。どちらかで落ちた案は色の物差しの結果に依らず採らないので、判断は変わらない。トレードオフの例外として全件を回す案は、色の物差しも回して数字に入れる。
6. **視覚レビュー（必須）** — 数値だけで判断せず、出荷される実 C# の出力を目で見る:
   ```
   python tools/visual_review.py compare            # 他人の未コミットを入れないなら、自分の変更を git add して compare --index
   ```
   パネルは窓で行き着く状態だけで、`dev_safe/Tests/visual_review/compare/`（状態 (b) の 5 色・除外つき・再現データ）と `dev_safe/Tests/workflow_review/compare/`（状態 (a)・(d)）にある。パネルの下に塗った状態（クリック位置・自動調整の有無・許容範囲・塗り先）が書いてある。
   - **変化の有無は機械の比較で決める**（縮小したパネルは同じ絵を「違う」と読み違えることがある）。元データは `dev_safe/Tests/visual_review/change_summary.json` の `changed` と `dev_safe/Tests/workflow_review/review.json` の `changed_from_snapshot`。compare は確かめるパネルだけを一覧に出す。変化 0（変更前とビット一致）のパネルは読まなくてよい。変更前が無いパネル（表に無い・null）は変化ありとして扱う。
   - **目は中身の良し悪しを見る。** 一覧のパネル PNG を **Read ツールで 1 枚ずつ**確かめる: 元に無い質感・ノイズが足されていないか／変換したい所に漏れが無いか／関係ない所が変わっていないか（**全体サムネイルで必ず確認**。切り出して作業したときも切り出しの外を見る）。
   - 問題があれば採用せず手順 4 へ戻る。問題が無ければ `python tools/visual_review.py approve --note "<変化したケースと目視した範囲・判断根拠、変化 0 で読まなかった件数>"`。
   - 承認は時刻でなく測った中身に結び付く。pre-commit は、ステージしたファイルが「HEAD と同じ」か「承認した比較で測った中身と同じ」なら通す（ファイル単位。1 つのファイルの hunk を分けると落ちる）。コミットの前に `python tools/visual_review.py check --index` で確かめられる。dev_safe の測定器・基準をステージしたコミットにも、dev_safe のフックが同じ承認を求める。
7. **判定** — 物差しと視覚レビューの両方が OK なら採用。悪化・横ばい・目で見た問題があれば破棄か別仮説へ。**改善が頭打ちになるまで 4〜6 を繰り返す。**
8. **記録** — 何を試して何が効いた／効かなかったかを簡潔にまとめ、最終報告に含める。

## 停止条件
次のいずれかでサイクルを止めて報告する。
- 指標がこれ以上有意に改善しない（数回試して改善幅がノイズレベル）。
- さらなる改善に GT の追加・仕様判断など **ユーザーの判断が必要**。
- 変更範囲がユーザー要求の外に広がりそう（勝手にスコープを広げない）。

## 汎化能力を最優先する
このツールの価値は「手元の数枚で完璧に動く」ことではなく、**未知のテクスチャでも妥当に動く**こと。
- **評価は複数アバター・複数衣装を横断する。** 回帰を丸ごと回し、個別と平均の両方を見る。再現率だけでなく**適合率（過検出）も同時に見る**。単一ケースの改善だけで採らない。1 ケースが良くなっても他が悪くなれば原則不採用（避けられないトレードオフは、悪化が小さく全体が良くなることを数値で示し、理由を報告に残す）。
- **特定のキャラ名・ファイル名・画素座標・色値で分岐しない。** 閾値・係数はテクスチャの統計量（ヒストグラム・彩度分布・領域サイズ比など）から導く。足す・変える定数は `docs/algorithm-constants.md`（定数の台帳）に種類と根拠を書く（食い違うと `scripts/source_checks/test_algorithm_constants.py` が落ちる）。台帳の「実測」「不明」は減らす候補で、新しい被写体で外れたときに最初に疑う先。
- 迷ったら、**より単純で仮定の少ない方**を選ぶ。アニメ調全体に成り立つ前提（セル影・乗算の影・部品ごとの単色の地色など）は使ってよいが、手元のアバターの描き方にだけ成り立つ規則は入れない。
- **汎化を確かめる単位はアバター**（被写体の数ではない。`dev_safe/Tests/subjects.json` の `subject_groups`。開発側は 9 体・33 被写体）。1 体の失敗をきっかけに段や定数を足すと、その塗り方の癖に合ってしまう（2026-10-19〜21 のサイクルで、手元の改善がホールドアウトにほとんど届かなかった）。

### 採否の物差し（過学習を防ぐ。2026-10-23〜）
- **選択（どこを塗るか）を変える変更**: `python dev_safe/scripts/generalization_report.py run --label <名前> --sieve` → `compare <候補の JSON> --motivated-by <きっかけのアバター>`（B だけ渡すと基準と比べる）。合格の目安は次のすべて（加えて compare は、位置の幅のアバター平均が広がらないこと・上下反転で変わる件数が増えないことも見る）:
  1. 開発に使ったクリック（p25/p50/p95）と使っていないクリック（p05/p75/p99）の両方で、ケースごとの退行床（`SELECTION_SLACK`）の違反が 0。
  2. どのアバターも平均（design IoU）が 0.005 より下がらない。
  3. きっかけのアバターを除いた平均が下がらない（改善と言うなら上がる）。1 体でしか効かない変更は採らない。
  4. 使っていないクリックの平均が下がらない。
  5. 色の近さだけで選ぶ素朴な基準線（クリック画素の色から ΔE76 ≤ 16 の球）に 0.05 以上負けたケースの数が増えない。
  合格してから `holdout_eval.py` を 1 回見る。
- **差の確からしさを書く（2026-11-16〜）。** compare と `holdout_eval.py` はアバター平均の Δ に、アバターを単位にした 95% 区間と符号反転の検定の p を付ける（`dev_safe/scripts/cluster_stats.py`。合否は変えない）。**「改善」と呼んでよいのは、区間の下限が 0 より上で p < 0.05 のときだけ。** そうでなければ「悪化なし・改善は確かめられず（+0.003、95% [−0.001, +0.008]、p=0.12）」のように数字ごと書く。開発側は 9 体しかないので、小さい差はたいてい確かめられない。段や定数を足す（複雑にする）変更で、どちらの物差しでも改善が確かめられないときは、足す理由を報告に書き、単純にする代案（足さない・既存の値を動かす・ほかの段を外す）が無いかを先に確かめる。
- **段を外す変更（簡素化）も同じ物差しで採る。** 外しても 1〜5 を満たすなら外す方を選ぶ。
- **定数は掃引して「台地の中ほど」を選ぶ。** 値ごとに `run`（掃引では `--sieve` を付けない）した結果を `sweep 値=JSON …` に渡し、台地（最良から 0.003 以内の値の幅）とアバターを 1 体ずつ外した成績（LOAO）を見る。最良の 1 点ではなく台地の中ほどを選び、隣の値で 0.01 以上落ちる崖の際は選ばない。外すアバターで選ぶ値が変わる定数は「手元の顔ぶれに敏感」と記録する。
- **境の定数を足す前に、境の両側を測る（2026-11-18〜）。** 「この量がこれを超えたら別の処理へ切り替える」形の定数を足す・動かすときは、境で結果が変わる例を全部集め、量の値ごとに「切り替えた方が良い／悪い」を数える。両側に良い例と悪い例が混ざるなら境の位置に根拠は無いので、境を動かさず、切り替えそのものが要らない作りを探す（2〜3 の失敗例の間に置いた値は「実測」でも根拠にならない。例: dev_safe の `docs/anchor-other-hue-2026-11-17.md`）。
- **再着色（どう塗るか）だけを変える変更**は選択の数字を動かさない（汎化レポートの IoU が一致することで確かめる）。**再着色の採否は、元のテクスチャとの見た目の一致（品質の物差しの形・コントラスト・ノイズと視覚レビュー）を優先する**（2026-11-16 ユーザー判断）。PSD の地の色を替えて重ね直した正解（`dev_safe/_spike/recolor_gt/psd_recolor_gt.py`）は理屈の上で正しい色を示すが見た目が元から変わることがあるので、参考の物差しにとどめ、これだけで採らない。色の物差し（`probe_target_chroma.py` など）は PSD が要らないので、GT の無いテクスチャでも測り、手元の塗り方に偏らないようにする。
- **指定した色に合うかを毎回比べる（2026-11-18〜）。** 選択か再着色を変える変更は `python dev_safe/scripts/color_report.py run --label <名前>` を回し（ホールドアウトは使わない。回すのは回帰と汎化レポートのふるいが通った後。手順 5）、`compare <B.json>` で基準と比べる。合格の目安は compare の判定（どのアバターの平均も 0.005 より悪くならない・悪くなったケースが良くなったケースより多くない・品質ゲートの違反と許容範囲の隣の段での飛びが増えない）。許容範囲の掃引は段ごとの良し悪しも読む（クリックごとの最悪の段だけではほかの段の悪化が隠れる。2026-11-18 に見落とした）。きっかけはユーザーの「出力の色がどんどん変わっている」。見た目の一致と両方を満たす: **地色は指定した色に、陰影・質感は元のとおりに。**
- **品質の物差し・元に無い線・ハイライトの再現**: 品質ゲート（`test_recolor_quality_gate`）は凍結した基準からの退行を見る物差し。選択を変えたらハイライトの再現（`highlight_recall.py`）も見る（IoU には出ない）。

### 基準を進める
採用した変更で物差しの値が動いたら、測った JSON を freeze して基準を進める。基準の一覧と作り直しのコマンドは dev_safe の `Tests/README.md`。主なもの:
- 1 つの基準 `generalization_reference.json`: `generalization_report.py freeze <JSON>`。pytest の床・名前つきの床・右クリックの後の床・視覚レビューの退行の判定が同じものを読むので、freeze 1 回で全部が進む。
- 色の物差し `color_reference.json`: `color_report.py freeze <JSON>`。品質の物差し `quality_gate_reference.json`: `quality_report.py --freeze`。
- 基準を付け替えるコミットには、**独立した正解（PSD の GT・お手本・指定色）に照らして良くなったか**を書く。「新しい出力を新しい基準にした」だけの付け替えにしない。基準のファイルをステージしたコミットにも視覚レビューの承認が要る。

### ホールドアウト
- `tools/workflow_contract.py` の `HOLDOUT_SUBJECTS`（一覧は `subjects.json` の `holdout_subjects`）は調整に使わない被写体で、開発側の `SUBJECTS` と交わらない。ユーザー決定により、既存の被写体は動かさず、**新しい GT はホールドアウトへ入れる**。
- 改善サイクル中はホールドアウトの個別の数字や絵を見ない。採否判断のときだけ `python dev_safe/scripts/holdout_eval.py` で集計値を見る（1 つの変更につき 1 回まで。前回より悪ければ終了コード 1）。
- **見た回数は「アルゴリズムを変えて採否を決めるために数字を見る」ことを数える（2026-11-23 ユーザー判断）。** 測定器の確かめ（並列化など）で、製品の DLL が同じものを回しても数えない。`holdout_eval.py` は同じ DLL・設定・被写体の集合の記録が既にあれば `repeat` を付けて残し、見た回数に数えない。直列と並列の突き合わせは `--verify-parallel`（値は出さず一致・不一致だけ。記録もしない）。
- ホールドアウトと同じ画像は、開発側の物差し・お手本に入れない（2026-11-21 ユーザー判断で、重なっていたお手本 2 例と色の物差しの素材を外した）。
- **入れ替える。** 被写体ごとの延べの回数（その被写体を含む集合を見た回数。競合との比較で見た分も数える）が 20 回に届いたら `holdout_eval.py` が知らせる。次に GT を足すとき、届いた被写体を開発側へ移し、新しい被写体をホールドアウトにする。新しい GT は、手元に無い描き手・塗り方（平塗り・厚塗り・淡い色が隣り合う配色など）を優先する。

## 回すテストの選び方
- 変更から回すテストを選ぶには `python tools/test_select.py`（`--index`・`--rev A..B`・`--run`）。UI・Infra だけなら回帰 FULL は要らない。ハーネス範囲・測定器なら回帰と視覚レビューを必ず出す（`docs/testing-architecture.md`「変更から回すテストを選ぶ」）。

## テストを足す・変えるとき
- 台帳（`roles.json`）に役目と入口を書く。1 つの関数に役目を混ぜない（混ざるときは付け替えの要る方を役目にし、note に「混在:」と書く）。消すときは台帳の `retired` に、守っていたこと・最後の結果・行き先を書く。
- 品質を測るテストの入口は窓の状態 (a)〜(d)（`oneshot.py`）にする。**固定設定（`fixtures.make_zone`）や従来の自動調整を入口にした品質のテストを足さない**（固定設定は合成の契約テストと abcheck の固定のシナリオ用。2026-11-20 ユーザー「普通に使っていて直っているのならテストが悪いだけ」）。
- 内部の値（診断の文字列・導いた許容など）を見る assert は足さない。出力で言える契約か、正解に照らした物差しにする。前の出力との完全一致は視覚レビューに任せる。
- **確かめていない物差しを関門にしない。** 物差しは、お手本と同じ向きの答えを出すか・過去にユーザーが見つけた悪化を捕まえるか・ユーザーが良いと言った変更を止めないかを確かめてから合否に使う（品質ゲートは新しい入口で目と合わず、2026-11-21 に絶対のしきい値の合否から外した）。
- お手本を足すときは `dev_safe/Tests/exemplars/README.md` の「足し方」に従う（幅はユーザーの答えだけから作る）。

## やってはいけないこと
- アバター・衣装のテクスチャや、そこから作った GT・特徴量で機械学習のモデルを作る（分類器を当てはめる・学習させる）こと。捨てる前提の実験でも先にユーザーに聞く（作品の規約に AI の利用を禁じる・控えるものがあり、CREDITS.md のデータの扱いとも食い違いうる。2026-11-01 に聞かずに当てはめた実験があった）。閾値・定数をテクスチャで掃引して選ぶのは学習に当たらない。
- GT・お手本と突き合わせずに「良くなった気がする」で終える。
- 手元のテストデータに最適化したパラメータを入れる（過学習）。個別ケースを通すためのハードコード、テクスチャ名・ハッシュ・特定色・座標を直接参照するロジックも同じ。
- テストを削除・無効化して「パスした」と報告する（消すなら台帳の `retired` に理由と行き先を残す。`[Ignore]` で黙らせない）。お手本の幅を製品に合わせて動かす。
- 悪化した変更をコミット対象に残す。
- 視覚レビューを省略してコミットする（`compare` → 変化したパネルを Read で 1 枚ずつ確認 → `approve` の順を飛ばさない）。これは pre-commit フックが要求する出荷ゲートで、省くと数値では見えない退行が出荷される。
