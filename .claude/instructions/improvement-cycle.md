# 自律的な改善サイクル

色抽出・マスク生成・領域判定など再着色アルゴリズムの品質改善は、**ユーザーの都度指示を待たず、エージェント自身が自律的にサイクルを回して** 進める。1 ステップごとに「次やりますか?」と聞かない。

## 測る対象は常に「実 C#」
- **製品 C#（`Code/Core/PixelProcessor.cs` ほか）が唯一の正。** 改善の良し悪しは、実 C# をそのまま動かす headless ハーネス経由の出力で判定する。アルゴリズムの Python 再実装を作って測らない（過去、Python プロキシが製品から IoU 0.26 乖離して改善サイクルが製品でなくプロキシを測っていた）。テスト構成・実行方法は `docs/testing-architecture.md` が正。

## 正解データ (Ground Truth)
- **PSD のレイヤー情報を「正」とする。** GT マスク/領域は `dev_safe/scripts/` 配下の GT 生成スクリプト（`build_*_gt.py` / `analyze_*_psd.py` 等）で PSD から作る。
- テクスチャ単体の目視結果や経験則は補助情報。PSD レイヤーと矛盾したら PSD を優先する。
- GT が不足しているなら、GT なしで「改善した」と主張せず、新しい GT を追加する。

## サイクルの基本形
1. **現状計測** — 実 C# ハーネス経由のテストでスコア・失敗ケースを数値で把握する:
   ```
   python -m pytest dev_safe/Tests/regression/ -q
   ```
   採否判断に使う計測（この手順 1 と手順 5）では、環境変数 `IROCA_CSHARP_GATE_FULL=1`（旧名 `VACC_CSHARP_GATE_FULL` も効く）と `VACC_AUTOTUNE_GATE_FULL=1`（こちらは旧名だけが効く）を立てる。立てないと品質ゲートは 1 被写体しか測らず、残りを測らないまま「全パス」と見誤る。
2. **失敗分析** — 最もスコアを落とす／誤検出・見逃しが目立つケースを特定し、原因を具体的に仮説化する（色空間、閾値、連結成分処理、マスク膨張/収縮など）。
3. **変更前スナップショット** — 変更前に必ず実行（旧出力を保存。すでに変更済みならスキップ可）:
   ```
   python tools/visual_review.py snapshot
   ```
4. **変更** — 仮説に基づく最小の変更を 1 つだけ加える。複数の改良を同時に混ぜない（どれが効いたか分からなくなる）。
5. **再計測** — 同じテストを実行し、全体スコアと個別ケースの変化を比較する。選択を変えたなら
   `dev_safe/scripts/generalization_report.py` でアバター別・未使用クリック・素朴な基準線も比べる（下の「過学習を防ぐ採否の物差し」）。
6. **視覚的レビュー（必須）** — 数値だけで判断せず、出荷される実 C# 出力で目視する:
   ```
   python tools/visual_review.py compare --engine csharp
   ```
   変更前から出力が変わったケースの比較パネル PNG を **Read ツールで 1 枚ずつ** 確認する（各画像は「元テクスチャ／変更前／変更後」の 3 列構成。変化したケースには 2 段目に等倍の切り出しが付く）。compare は確認するパネルだけを一覧に出す。変化の有無の元データは、固定設定が `dev_safe/Tests/visual_review/change_summary.json` の `changed`、ワークフローが `dev_safe/Tests/workflow_review/review.json` の `changed_from_snapshot`。
   - 変化が 0 のケース（変更前とビット一致）は読まなくてよい。
   - 変更前が無いケース（change_summary.json に載っていない、`changed_from_snapshot` が null）は変化ありとして扱う。

   確認するケースで以下をチェックする:
   - 元テクスチャにない質感・ノイズが追加されていないか
   - 変換対象エリアに変換漏れがないか
   - 関係ない部分が変わっていないか（**全体サムネイルで必ず確認**）
   - テクスチャを切り出して作業した場合も、全体サムネイルで切り出し範囲外が変わっていないか

   問題があれば採用せず手順 4 へ戻る。問題がなければ承認マーカーを書く:
   ```
   python tools/visual_review.py approve --note "<変化したケースと目視した範囲・判断根拠、変化 0 で読まなかった件数>"
   ```
7. **判定** — IoU スコアと視覚レビューの両方が OK なら採用。悪化・横ばい、または視覚的問題があれば破棄か別仮説へ。**改善が頭打ちになるまで 4〜6 を繰り返す。**
8. **記録** — 何を試して何が効いた/効かなかったかを簡潔にまとめ、最終報告に含める。

## 停止条件
次のいずれかでサイクルを止めて報告する。
- 指標がこれ以上有意に改善しない（数回試して改善幅がノイズレベル）。
- さらなる改善に GT の追加・仕様判断など **ユーザーの判断が必要**。
- 変更範囲がユーザー要求の外に広がりそう（勝手にスコープを広げない）。

## 汎化能力を最優先する
このツールの価値は「手元の数枚で完璧に動く」ことではなく、**未知のテクスチャでも妥当に動く** こと。改善サイクルは常に汎化を意識して回す。

- **評価は複数キャラ/複数衣装を横断して行う。** `dev_safe/Tests/regression/` を丸ごと回し（`*_iou` 系・`false_positive` 系を含む）、個別スコアと平均の両方を見る。単一ケースの改善だけで採用しない。
- **1 ケース改善しても他ケースが悪化したら原則不採用。** 避けられないトレードオフは、悪化幅が小さく全体平均が向上することを数値で示し、理由を報告に残す。
- **特定キャラ名・ファイル名・ピクセル座標・色値で条件分岐しない。** 閾値・係数はテクスチャの統計量（ヒストグラム、彩度分布、領域サイズ比など）から導く。マジックナンバーを足すなら、なぜ他でも妥当かを説明できること。
- **ホールドアウトで汎化を確かめる**（2026-09-24 に枠を用意）。`tools/workflow_contract.py` の
  `HOLDOUT_SUBJECTS` は調整に使わない被写体で、`SUBJECTS`（回帰の床・審査ページ・視覚レビュー）とは
  交わらない。ユーザー決定により、既存の被写体は動かさず、**次に GT を足すときからホールドアウトへ入れる**。
  改善サイクル中はホールドアウトの個別の数字や画を見ない。採否判断のときだけ
  `python dev_safe/scripts/holdout_eval.py` で集計値を見る（実行ごとに記録され、見た回数が出る。
  1 つの変更につき 1 回まで。前回より悪化していれば終了コード 1）。
- **過検出を見ないテスト（`false_positive` 系）を特に重視する。** 再現率(Recall)だけでなく適合率(Precision)を同時に見る。
- 迷ったら、**より単純で仮定の少ない方** を選ぶ。複雑なヒューリスティックは未知データで壊れやすい。

### 過学習を防ぐ採否の物差し（2026-10-23〜）
手元の回帰の被写体は 19 件あっても、描いた人（アバター）で数えると 4 組しかない（`dev_safe/Tests/subjects.json` の
`subject_groups`）。1 体の失敗をきっかけに段や定数を足すと、その塗り方の癖に合ってしまう（手元の改善がホールドアウトに
ほとんど届かなかった、2026-10-19〜21 のサイクル）。**汎化を確かめる単位は被写体の数ではなくアバターの数**とする。
アニメ調のアバターに寄せること自体は問題ではない（セル影・乗算の影・パーツごとの単色の地色など、アニメ調全体に成り立つ
前提は使ってよい）。問題は、手元のアバターの描き方にだけ成り立つ規則を入れること。

- **選択（どこを塗るか）を変える変更**は、採否の前に
  `python dev_safe/scripts/generalization_report.py run --label <名前>` を回し、
  `compare <基準の JSON> <候補の JSON> --motivated-by <きっかけのアバター>` で比べる（基準は `freeze` した
  `Tests/Baselines/generalization_reference.json`。B だけ渡すとこれと比べる）。合格の目安は次のすべて:
  1. 開発に使ったクリック（p25/p50/p95）と使っていないクリック（p05/p75/p99）の両方で、ケースごとの退行床
     （`SELECTION_SLACK`）の違反が 0。
  2. どのアバターも平均（design IoU）が 0.005 より下がらない。
  3. きっかけになったアバターを除いた平均が下がらない（改善と言うなら上がる）。1 体でしか効かない変更は採らない。
  4. 使っていないクリックの平均が下がらない。
  5. 色の近さだけで選ぶ素朴な基準線（クリック画素の色から ΔE76 ≤ 16 の球）に 0.05 以上負けたケースの数が増えない。
  合格してから `holdout_eval.py` を 1 回見る。採用したら `generalization_report.py freeze <JSON>` で基準を進める。
- **段を外す変更（簡素化）も同じ物差しで採る。** 外しても 1〜5 を満たすなら、外す方を選ぶ。
- **定数は掃引して「台地の中ほど」を選ぶ。** 値ごとに `run` した結果を `sweep 値=JSON …` に渡し、台地（最良から 0.003 以内の
  値の幅）と、アバターを 1 体ずつ外して選び直したときの成績（LOAO）を見る。最良の 1 点ではなく台地の中ほどを選び、
  隣の値で 0.01 以上落ちる崖の際は選ばない。外すアバターによって選ぶ値が変わる定数は「手元の顔ぶれに敏感」と記録する。
- **再着色（どう塗るか）だけを変える変更**は選択の数字を動かさない（`generalization_report` の IoU が一致することで
  確かめる）。色の物差し（`dev_safe/scripts/probe_target_chroma.py` の明るい面の彩度 ÷ 目標など）は PSD の正解が
  要らないので、手元の被写体に加えて GT の無いテクスチャでも測り、4 体の塗り方に偏らないようにする。
- **ホールドアウトは入れ替える。** 被写体ごとの延べの回数（その被写体を含む集合を見た回数。競合との比較で見た分も
  数える）が 20 回に届いたら、`holdout_eval.py` が知らせる。次に GT を足すとき、届いた被写体を開発側（`SUBJECTS`）へ移し、
  新しい被写体をホールドアウトにする。新しい GT は、手元に無い描き手・塗り方（平塗り・厚塗り・淡い色が隣り合う配色など）を
  優先する。

## やってはいけないこと
- GT と突き合わせずに「良くなった気がする」で終える。
- 手元のテストデータに最適化したパラメータを入れる（＝過学習）。個別ケースを通すためのハードコードや、テクスチャ名・ハッシュ・特定色・座標を直接参照するロジックも同じ。
- テストを削除・無効化して「パスした」と報告する（必要なら `[Ignore]` でなく理由をログに残す）。
- 悪化した変更をコミット対象に残す。
- 視覚的レビューを省略してコミットする（`compare --engine csharp` → 変化したケースを Read で 1 枚ずつ確認 → `approve` の順を飛ばさない）。これは pre-commit フックが要求する出荷ゲートであり、「念のための再確認」ではない。省くと数値では見えない退行が出荷される。
